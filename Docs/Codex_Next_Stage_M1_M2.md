# CODEX — RoadToWisdom: стабилизация M1 и подготовка M2

## Контекст и обязательные источники

Это существующий **Unreal Engine 5.8 C++ проект RoadToWisdom**, художественное название игры Quiet Road. Проект создан из стандартного Vehicle Template. Игра одиночная: управляемый дом на колёсах/фургон, выход пешком, исследование заброшенного района, интерактивные инженерные задачи. Приоритеты: **реальная работоспособность, переиспользуемые UT plugins, понятный минимальный C++, маленький Git**.

Прежде всего:
- Прочитай корневой `AGENTS.md` и применимые локальные инструкции; проверь проект/плагины.
- Прочитай `Docs/Quiet_Road_GDD_v0.2.md` (или актуальный путь к GDD), особенно §§7, 10, 12, 17, 21–26.
- Если есть `Docs/ToolkitIntegrationMatrix.md`, `REUSE_GUIDE`, спецификации Toolkit и другие docs, читай их **до изменения API**.
- Ознакомься с текущими `Gameplay/RoadToWisdomExplorerController`, `Gameplay/Character/RoadToWisdomOnFootCharacter`, `Gameplay/Missions/*`, `Gameplay/UI/*`, базовыми template-классами и реальными API UT plugins.
- Сначала получи status Git, выясни, что изменено пользователем; не теряй его правки. Не переименовывай проект или папки ради художественного названия.

**Не создавай новый framework:** взаимодействия/инвентарь/сохранения/мировые механики должны использовать имеющиеся UT plugins. Не менять их API, публичные контракты и GDD без убедительной причины и документирования. Не подключать GAS, StateTree, SmartObjects и Full Toolkit по умолчанию. Не добавлять Battle/Co-op в одиночную карту.

## Этап 1 (сейчас, обязательный): исправить первичные блокеры

### A. Enhanced Input
- Убери `ConstructorHelpers::FObjectFinder` из `ARoadToWisdomOnFootCharacter::SetupPlayerInputComponent`: он допустим в конструкторе, но не в обычном методе.
- Аккуратно разрешай Input Actions через ctor/редакторские properties (с сильными UObject references и без hidden runtime string loading); события bind в `SetupPlayerInputComponent`.
- Проверяй карту: проектные IA/IMC реально существуют; если не существуют — создать **настоящие uasset через UE Editor/Python/MCP**, не имитировать их текстом. Не переписывать template управление автомобилем.
- Убедись, что F обрабатывается ровно один раз в каждом режиме, E работает только пешком, водительские actions не остаются активными после выхода.

### B. Постоянный автомобиль
- Сейчас `ARoadToWisdomQuietRoadGameMode` стартует пешком, а `ARoadToWisdomExplorerController::VanPawn` заполняется только при `OnPossess(ARoadToWisdomPawn)`. Проверь реальную карту и поправь инициализацию.
- Должен быть **один placed vehicle actor**, единственный источник истины, независимо от факта possession. В простом случае однократно обнаружь помеченную машину при инициализации, проверь ровно один результат и сохрани `UPROPERTY` ссылку; либо используй существующую explicit level reference, если она уже настроена. Не делать поиск каждый Tick и не плодить singleton/manager ради одного актора.
- Сохрани существующее `OnFoot` начало, если оно уже предусмотрено картой и GDD. Сразу при старте можно подойти и нажать F, уехать, выйти и вернуться. Не создавать второй фургон автоматически.

### C. Восстановление состояния
- Проверь событие/порядок `BeginPlay`, `OnPossess`, создание on-foot pawn, регистрацию placed vehicle. Существующий pending restore назначается в BeginPlay и применяется только при срабатывании OnPossess. Исправь, чтобы restore сработал ровно раз и при любом корректном порядке старта.
- Сохранять и загружать состояние фургона, режима владения, player transform, inventory, world snapshot, стадию миссии. Проверить повторный запуск, переходы F, отсутствие дублей.
- Проверить FUTResult у `WriteSection`, `CaptureWorldState`, `SaveToSlot`, `LoadFromSlot`; не считать partial-save успешным и не оставлять UI ложного успеха. Не переписывать внутреннюю систему сохранения плагина.
- Сверить сериализацию рычага / fuse box / inventory с реальными API Toolkit; Load не должен вызывать повторную выдачу награды или выполнять заново коммит шага.

### D. Корректность взаимодействия и UI
- Проверить капсулой свободное место при выходе, землю под ногами и запас для двери. Запрет выхода на ходу сохранить. Для посадки проверять близость к водительской двери, а не только к origin центра длинного фургона, с простыми редактируемыми настройками/scene component при необходимости.
- После создания HUD должны сразу отображаться текущая цель и режим, независимо от порядка BeginPlay; UI и контексты не должны дублироваться при 10 циклах F.
- Проверить UTInteractor focus/hold behavior с ручным UpdateFocus; не допускать второго trace/prompt framework.
- У `FuseBox` проверить уникальность постоянного SaveStableId, одноразовость расходования предохранителя и видимость после restore. При нескольких одинаковых actors с ID — диагностика, не тихая порча сохранения.

## Этап 2 (после прохождения этапа 1): завершить первую игровую петлю

Добавь к фургону **минимальную интерактивную радиопанель**, только если уже стабильны посадка/первая миссия/загрузка:
- На стоящем фургоне пешеход нажимает E на панели / интерактивной точке; получает текущую цель и краткое сообщение о восстановлении ретранслятора.
- Реализовать через UTInteraction; не создавать generic radio system или большую UI/Quest архитектуру.
- Радио позволяет **сохранить прогресс** через существующий SaveCoordinator в валидном безопасном состоянии; показывать успешное сохранение только если `FUTResult.IsSuccess()`.
- Проверить `new game → установить fuse → lever → вернуться → сохранить → перезапустить → тот же прогресс`, включая случаи отсутствующего/битого slot.
- Если Toolkit предоставляет готовую функцию взаимодействия с контейнером/хранилищем, можно подключить маленький багажник. Если нет — **не разрабатывать дублирующий Inventory Framework** и отложить багажник до следующего этапа.

## Этап 3 (только если предыдущие два реально проверены): первый визуальный эталон M2

Не строить весь мир. Создать/доработать **один небольшой красивый участок ~250×250 м**: проезжаемая дорога, стартовая стоянка, ретранслятор, несколько вариантов растительности и камней, один целостный пресет освещения/тумана. Основной инструмент — редактируемый PCG/Editor Utility/Python Editor Script, а не ручная расстановка сотен объектов.

- Проанализировать уже существующую карту/ассеты и переиспользовать их; не перезаписывать авторскую сцену.
- Сделать детерминированное editor-time размещение декора по seed, плотности, исключениям дороги/POI/двери; проверять склон и clearance.
- Дорога и сюжетный объект остаются фиксированными; не делать генератор бесконечных дорог, сложный world streaming и новые terrain frameworks.
- Маленькая согласованная палитра, низкая детализация мешей, общие материалы/instances; никаких тяжёлых Fab packs/4K textures/Megascans.
- Для массового декора применять ISM/HISM/PCG подходящим образом, не создавать Actor на куст. Сохранение mission не зависит от повторной генерации природы.
- Если UE Python/MCP недоступны, подготовить воспроизводимый editor script и точные шаги запуска, но не заявлять, что карта реально создана.
- Проверить проходимость машиной и пешком, видимость объектов и реальный облик в редакторе (хотя бы скрин/сводку визуальной проверки, если доступно).

## Размер и Git

- Сохранять нужные `.uasset`/`.umap` и исходники генератора; игнорировать Binaries/Intermediate/Saved/DerivedDataCache и иные кэши в игре и plugin modules.
- Проверить tracked content и крупнейшие файлы до/после. Внутренний бюджет M1/M2: 250 MiB контента; >50 MiB анализировать отдельно; >100 MiB не класть в обычный Git. Git LFS **не включать автоматически** без разбора существующей конфигурации.
- Не удалять template variants/assets без доказанной неиспользуемости. Перед перемещением/переименованием Unreal assets проверить redirectors/references в Editor.
- Не делать широкого рефакторинга template-кода ради красоты, не заводить временные параллельные компоненты.

## Проверки, которые должны быть в конце

1. Исходный Vehicle Template продолжает ехать; переход к OnFoot и обратно работает не менее 10 раз.
2. В стартовой карте одна registered VanPawn; без ссылок nullptr.
3. На движении F отклоняется, у стены/дерева выход безопасен или корректно запрещён, у водительской двери F сажает.
4. Интеракция fuse/lever происходит один раз; у повторного E нет побочных эффектов.
5. Save/load после 3 разных точек: на ногах, в фургоне, после completed; state консистентен без item duplication.
6. Для HUD цель отображается как после clean start, так и сразу после load.
7. Реальная компиляция UE 5.8 и реальные PIE/Standalone тесты, если среда доступна; если нет — не объявлять PASS, указать блокеры, команды и ручные действия.
8. Отчёт по размерам Git/Content, plugin dependencies, проверенные API UT.
9. Обновлённые короткие `Docs/TestingChecklist.md`, `Docs/ToolkitIntegrationMatrix.md`, `Docs/Architecture.md`/`HowToRun.md` только при необходимости; без раздутой документации.
10. `git diff --check`, отчёт по изменённым файлам и отсутствие неучтённых user changes.

## Ограничения реализации

- **Не меняй поведение игры по собственному усмотрению:** действующий GDD главный, при сомнениях явно зафиксируй допущение.
- Упрощай: небольшие методы, минимальное количество состояний, ответственность класса соответствует Gameplay Framework UE. Исключить лишние `Tick`, manager, delegates, копии plugin API, преждевременные абстракции.
- Используй существующие `AGENTS.md`, `REUSE_GUIDE` и фактические Toolkit modules. Если найден дефект внутри переиспользуемого плагина, опиши его отдельно, не ломая plugin code ради локального обхода молча.
- Сначала подтвердить работоспособность этапа 1 и только затем расширять сцену.

Если нет UE Editor/MCP, не выдавай предположения за результат. Создавай коммиты только по действующим проектным правилам, не скрывай изменения пользователя.
