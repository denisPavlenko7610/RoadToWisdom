# QUIET ROAD / «ТИХАЯ ДОРОГА»
## Game Design Document — v0.1

**Дата:** 24 октября 2026  
**Статус:** утверждённая рабочая концепция для первого прототипа; численные параметры предварительные  
**Движок:** Unreal Engine 5.8, C++  
**Стартовая основа:** Games → Vehicle → Variant **None** → C++ (если выбран шаблон Blueprint, добавить C++ класс и модуль проекта)  
**Платформа:** Windows PC, клавиатура/мышь; геймпад — после основного цикла  
**Режим:** одиночная игра; мультиплеер — только независимые интеграционные проверки Toolkit, если в будущем потребуется  
**Жанр:** атмосферное компактное исследовательское приключение с управляемым домом на колёсах, лёгкими задачами и развитием оборудования

---

## 1. Цель проекта

Сделать небольшую интересную и технически добротную игру, которая одновременно:

1. Обучает разработчика практической работе с UE 5.8, C++, Chaos Vehicles, Enhanced Input, PCG, Gameplay Framework, сохранениями и инструментами редактора.
2. Проверяет **существующие** переиспользуемые domain plugins в условиях настоящей игры и их совместную работу.
3. Позволяет позже добавлять новые модули, **не превращая игру в бессвязный тестовый полигон**.
4. Требует минимум ручного моделирования и расстановки окружения: предпочтительны компактные наборы ассетов, генераторы и небольшие вручную утверждённые точки интереса.
5. Сохраняет контролируемый размер GitHub-репозитория и быструю сборку после клонирования.

**Правило приоритетов:** законченность игрового цикла > правильная интеграция существующих модулей > понятность C++ и обучающая ценность > автоматизация контента > дополнительные фичи.

## 2. Короткое описание и фантазия игрока

Герой едет в небольшом переоборудованном фургоне-доме по живописному заброшенному горно-лесному району. Несколько исследовательских станций неожиданно замолчали. Связь восстанавливается от точки к точке: игрок сам ведёт машину, останавливается, выходит наружу, изучает объекты, решает компактные задачи, приносит находки в фургон и улучшает переносное оборудование.

Это история об одиночном пути, любопытстве и постепенном возвращении жизни в тихий район; без обязательных сражений и сурового выживания. Атмосфера немного загадочная, но не хоррор.

**Отличительная особенность:** фургон — постоянная мобильная база и физический участник игрового цикла, а не экран выбора миссий. Игрок действительно водит его, паркует, выходит и возвращается к нему. Интерактивный мир небольшой, но последовательный и достаточно насыщенный.

## 3. Игровые столпы

1. **Ехать самому:** свободное управление машиной, без телепортации между локациями.
2. **Исследовать пешком:** выход из машины в любой безопасной точке и взаимодействие с окружением.
3. **Каждая остановка осмысленна:** небольшой объект, наблюдение, задача, полезный результат.
4. **Использовать, а не только собирать:** предметы и инструменты реально меняют возможности.
5. **Красиво благодаря стилю и процедурам:** читаемые силуэты, туман, освещение, небольшое число повторно используемых ассетов.
6. **Код остаётся главным:** минимум дорогостоящих анимаций, уникальных моделей, сюжетных роликов и систем ради самих систем.

## 4. Целевая аудитория и ожидаемая длительность

- Игроки, которым нравятся короткие самостоятельные путешествия, исследование и понятные инженерные задачи.
- **Первый игровой фрагмент (vertical slice):** 10–20 минут; один полностью завершённый выезд.
- **Компактная версия 1.0:** ориентир 45–90 минут, если игровое ядро окажется увлекательным. Не обязательство создавать все главы сразу.
- Повторное прохождение не является базовой целью; процедурные изменения декоративные и частично вариативные.

## 5. Мир и художественный стиль

### 5.1. Регион

- Один компактный игровой регион: **примерно 0,7–1,0 км на сторону** как стартовая целевая область; окончательный размер выбрать по времени поездки и производительности.
- Замкнутая или ветвящаяся грунтовая дорога длиной порядка 1,5–2,5 км; ответвления ведут к нескольким объектам.
- Лес, редкие деревья, низкие холмы, камни, кусты, лужи или сухой ручей без физического моделирования жидкости.
- 3 сюжетные точки интереса плюс стартовая площадка и финальная точка (финал может переиспользовать старт).
- Край региона перекрывается естественными препятствиями: склонами, густым лесом, ограждениями. Невидимые стены использовать только как подстраховку.

### 5.2. Визуальные правила

- Стилизованный low-poly / soft-stylized realism, **не фотореализм**.
- Один узнаваемый набор материалов: земля, гравий, трава, дерево, металл, пластик, стекло.
- Мягкое освещение позднего дня, холодный туман в низинах, тёплые фонари и свет фургона.
- Повторное использование модульных элементов и экземпляров материала; избегать десятков уникальных 4K текстур.
- Для генерации окружения использовать PCG / Instanced Static Mesh / HISM по мере необходимости, предпочтительно в редакторе.
- Не требовать больших внешних сцен, мегасканов, кинематографических пакетов или тяжёлых ассет-паков.

### 5.3. Автоматизация

- **Ручная работа:** отобрать 3–4 осмысленные площадки, проверить маршрут и безопасные места парковки.
- **Процедуры:** размещение деревьев, кустов, камней, мелких предметов, декоративных элементов вдоль дороги.
- **Инструменты:** редактируемые параметры seed, плотность, дистанция от дороги, запрет генерации на площадках заданий, уклон, список мешей.
- **Важно:** объекты, необходимые для выполнения задания, не должны определяться случайной генерацией. Их положение и устойчивые ID назначаются вручную/из данных.
- На старте генерация **в редакторе**, а не бесконечная runtime-генерация, чтобы упростить физику, сохранения, упаковку и отладку.

## 6. Основной игровой цикл

**Получить радиосигнал → отметить объект → самостоятельно доехать → безопасно припарковаться → выйти → исследовать и решить задачу → забрать результат → положить его в фургон/зафиксировать данные → открыть следующее направление или улучшение → ехать дальше.**

Пример на 7–10 минут:

1. Радио сообщает координаты молчащего ретранслятора.
2. Игрок едет по грунтовой дороге и замечает вышку.
3. Останавливается, выключает двигатель или ставит ручник, выходит.
4. Осматривает щиток: отсутствует предохранитель.
5. Находит предохранитель в соседнем ящике, подбирает через модуль Items.
6. Использует предохранитель на щитке через модуль Interaction, получает статус WorldMechanics.
7. Включает рубильник, слышит восстановившийся сигнал.
8. Возвращается к фургону; следующая точка появляется в журнале.

**Главный принцип:** задачи должны опираться на небольшое число общих действий, а не на уникальный скрипт для каждого здания.

## 7. Игрок: перемещение и камеры

- Вне фургона игрок управляет обычным `ACharacter`, третье лицо (для первой версии). Ходьба, бег, обзор, простой прыжок — только если нужен для геометрии.
- Использовать существующего персонажа или движковые базовые средства; не разрабатывать сложную анимационную систему ради прототипа.
- Камера автомобиля — из Vehicle Template, с аккуратной настройкой дистанции.
- В будущем допустим вид от первого лица, но он **не входит в MVP**.
- Переключать управление через `APlayerController::Possess` и разные Enhanced Input Mapping Contexts.
- UI и управление не должны оставаться активными в неверном режиме.

### 7.1. Посадка / выход

- Сесть: подойти к водительской двери в пределах небольшого расстояния и нажать F.
- Выйти: машина полностью или практически остановлена, выход свободен от препятствий и находится на допустимой поверхности.
- При выходе пешеход появляется у двери в безопасной точке, а не внутри коллизии машины.
- После выхода фургон остаётся на месте с безопасным торможением; камера переключается на персонажа.
- При посадке пешеход скрывается/деактивируется без уничтожения важного состояния; контроллер получает фургон.
- Если дверь заблокирована, попробовать заранее заданные альтернативные точки вокруг фургона; если ни одна не подходит, показать понятную причину отказа.
- Движущийся фургон нельзя покидать в MVP. Исключить переход из режима пешком при невалидном состоянии игры.

### 7.2. Дом на колёсах как объект

- **MVP:** один физически управляемый автомобиль + багажное отделение, радио, условная панель улучшений. Дверь/багажник могут быть простыми интерактивными точками.
- **Не в MVP:** свободная ходьба внутри движущегося фургона, полноценная мебель с физикой, переход от вождения к жизни в салоне без смены режима, сложные анимации посадки.
- На старте разрешено использовать машину из шаблона **как временный технический заменитель фургона**, пока нет подходящей лёгкой модели с корректным скелетом, колёсами и физическим ассетом. Замена меша не должна ломать код механик.
- Финальный художественный объект — компактный 4-колёсный camper van со скромным внешним оборудованием.

## 8. Управление (предварительное)

| Действие | Клавиши |
|---|---|
| Автомобиль: газ / тормоз / руль | W/S/A/D, совместимо с шаблоном |
| Автомобиль: ручной тормоз | Space |
| Фары | L |
| Выход из машины / посадка рядом с дверью | F |
| Пешеход: ходьба | WASD |
| Пешеход: обзор | Мышь |
| Взаимодействие с объектом | E |
| Инвентарь | I |
| Карта и цели | M |
| Журнал задания | Tab |
| Пауза | Esc |

Поведение Actions/Mapping Contexts централизовать через существующие возможности Enhanced Input. Конфликты со стандартными кнопками Vehicle Template устранить целенаправленно, не переписывая всю систему ввода.

## 9. Предметы, инструменты и прогрессия

### 9.1. Типы предметов

- Квестовые предметы: предохранитель, модуль связи, рабочий аккумулятор.
- Обычные находки: запчасти/металлолом — только если появится ясная функция обмена или улучшения.
- Инструменты: ручной диагностический прибор, универсальный ремонтный инструмент (второй — позже).

Предмет обладает ID, типом, визуальной ссылкой и опциональными параметрами; точная структура определяется существующим модулем `Items`, а не GDD.

### 9.2. Инвентарь

- Небольшой переносимый инвентарь, без сетки предметов и симуляции веса на старте.
- Багажник фургона — второй контейнер, если это поддерживает текущий Toolkit. В противном случае сначала сделать только один инвентарь и интерактивную точку для выгрузки результатов.
- Обязательна ясная обратная связь: подобрал, использовал, не хватает предмета, предмет потрачен.

### 9.3. Улучшения

- Радиосканер: показывает следующую станцию или точнее определяет сигнал.
- Фары: улучшают обзор в тумане/сумерках (если визуально заметно).
- Место для оборудования/багажник: открывает дополнительную возможность только при наличии соответствующей механики.

**Без гринда.** Улучшение является наградой за конкретную миссию, а не поводом многократно собирать одинаковый мусор.

## 10. Квесты и последовательность

Использовать простой журнал состояний миссий: `Unavailable → Available → Active → Completed` (в зависимости от существующих интерфейсов Toolkit). Никакой большой универсальной системы квестов заранее.

### Миссия 0. «Первый эфир» (обучение)

**Место:** стартовая лесная стоянка.  
**Цель:** запустить радиостанцию, понять маршрут, сесть за руль, доехать до первого указателя.  
**Механики:** управление, Interaction, UI, безопасная посадка, первая контрольная точка.  
**Готово, когда:** игрок понимает, куда ехать и как выйти из машины.

### Миссия 1. «Молчаливый ретранслятор» (первый вертикальный срез)

**Место:** небольшая вышка у дороги.  
**Цель:** восстановить питание.  
**Шаги:** припарковаться → найти ящик → подобрать предохранитель → установить → включить рубильник → получить сигнал.  
**Механики:** движение автомобиля и пешком, Interaction, Items, WorldMechanics, Progression, Save, простой звук/UI.  
**Награда:** доступ ко второй точке; улучшение радиосканера.  
**Особенность:** полностью проходимая миссия без врагов и без редких ассетов.

### Миссия 2. «Заваленный сервисный пункт»

**Место:** сарай/гараж у дороги.  
**Цель:** достать диагностический модуль и восстановить небольшой генератор.  
**Шаги:** отодвинуть лёгкое препятствие → взять устройство → применить к щитку.  
**Механики:** PhysicsMechanics, Items, WorldMechanics, Save; адаптация задачи под реально существующие модули.  
**Ограничение:** физическая задача не должна запирать прохождение из-за случайно улетевшего объекта; предусмотреть сброс объекта.

### Миссия 3. «Метеостанция»

**Место:** площадка датчиков на холме.  
**Цель:** восстановить питание и навести антенну.  
**Шаги:** проверить два узла прибором → активировать один механизм → включить станцию.  
**Механики:** Interaction, инструменты, WorldMechanics, SpawnMechanics (например, одно контролируемое событие после ремонта), прогрессия.

### Финал. «Ответ на частоте»

**Место:** стартовая стоянка или главная вышка.  
**Цель:** принять собранный сигнал и узнать происхождение тишины.  
**Реализация:** короткая интерактивная сцена и запись в журнале, без кинематографического ролика.

## 11. Системы мира и окружения

- **Радиосигналы:** подсказки о следующей цели и легальная причина для новых задач.
- **Электрические узлы:** выключатель, предохранитель, генератор, антенна; комбинировать из ограниченного набора повторно используемых компонентов.
- **Физические объекты:** лёгкие ящики/препятствия с контролируемыми ограничениями и способом вернуть в исходную позицию.
- **SpawnMechanics:** контролируемые находки/события, не случайный спавн всей карты.
- **Время суток:** фиксированное позднее время или 2–3 световых состояния, без обязательной сложной симуляции дня/ночи.
- **Погода:** базовый туман и небольшая атмосферная вариация; динамический дождь только после устойчивой производительности.

### 11.1. Сражения и опасности

У игры **нет обязательного боевого цикла**. Чтобы проверить `Combat` и `CombatMechanics` в будущем, допускается одна опциональная зона с неисправным дроном/турелью, чья атака/урон проверяют реальные компоненты Toolkit. В MVP нет врагов, оружия, здоровья, смерти или искусственного интеллекта противников. Если боевые плагины требуют собственной тестовой среды — отдельная интеграционная карта, а не насильственное внедрение в повествование.

## 12. Сохранения и устойчивость мира

Сохранять через существующий модуль `Save`, если его API действительно поддерживает необходимую задачу:

- версию формата сохранения и идентификатор мира;
- текущую миссию и завершённые шаги;
- инвентарь/предметы и открытые инструменты;
- улучшения фургона;
- состояние значимых узлов (починен/активирован, предмет уже собран);
- безопасную позицию и ориентацию автомобиля, а также режим управления.

**Не сохранять:** все процедурные кусты и деревья, каждый кадр физики, временные декоративные объекты.

В первой версии разрешено сохраняться только в безопасном состоянии: например, припаркованный фургон и игрок вне опасной операции. При загрузке, если точка занята или некорректна, возвращать машину в последнюю валидную стоянку. Состояние значимых объектов должно иметь устойчивые ID, независимые от порядка спавна и имён случайных Actor.

Сохранение и загрузка одного и того же этапа не должны повторно выдавать награду или бесконечно респавнить квестовый предмет. Изменения генератора окружения не должны ломать сюжетные сохранения.

## 13. UX и интерфейс

- В автомобиле: минимальный спидометр из шаблона (если удобен), текущая цель и подсказка F для выхода.
- Пешком: точечная подсказка E, компактный инвентарь, текущая задача.
- На карте: положение фургона и открытые точки, без сложной навигационной системы.
- Пауза и главное меню: Continue / New Game / Settings / Exit — реализовать постепенно.
- Подсказки объясняют причину невозможного действия: «Остановите фургон», «Дверь заблокирована», «Нужен предохранитель».
- Можно использовать простые иконки и шрифт движка; никаких больших UI-пакетов.

## 14. Аудио и история

- Звуковой облик: мотор/колёса (что уже есть в шаблоне или доступно легально), ветер, редкие птицы, электрические щелчки, радио-шум.
- Реплики необязательны: сюжет подаётся через короткие радиосообщения и записи. Озвучка — после MVP.
- Одна атмосферная музыкальная тема не обязательна; избегать тяжёлых наборов аудио.
- Игрок не получает штрафов за неторопливую езду или исследование.

## 15. Нефункциональные требования

### 15.1. Размер проекта и GitHub

- Внутренний целевой бюджет **отслеживаемого игрового контента** (без движка, кэшей и внешних submodules): **до 250 MiB для первого рабочего среза**, с запасом до **500 MiB** по мере развития. Это **цели проекта**, а не юридические лимиты GitHub.
- Не добавлять файл больше **50 MiB** в обычный Git без отдельного разбора, а файлы от **100 MiB** нельзя отправлять в обычный GitHub Git.
- Git LFS использовать осознанно для действительно больших бинарных файлов/часто изменяемых карт, учитывая квоты и рост истории. Git LFS не сжимает ассеты волшебным образом.
- Исключить из Git `Binaries/`, `Intermediate/`, `Saved/`, `DerivedDataCache/`, временные IDE/cache файлы и Cook/Build outputs, не потеряв исходники модулей.
- Избегать массивных Marketplace/Fab packs, Megascans и тысяч исходных текстур. Для сомнительных ресурсов проверить права на хранение в репозитории.
- Проверять, что «чистый clone» открывается с исходниками и доступными ассетами; сторонние плагины должны иметь воспроизводимое подключение.
- Следить за **историей** бинарных файлов: частые коммиты больших `.umap` увеличивают общий объём Git/LFS.

### 15.2. Производительность

- Цель — комфортные 60 FPS при 1080p на выбранном тестовом ПК; измерять после прототипа, не обещать абстрактных 60 FPS на любом железе.
- Применять инстансинг для массовых декоративных мешей, ограничить динамические источники света и тяжёлую прозрачность.
- Не создавать отдельный `AActor` на каждый декоративный камень/травинку.
- Не загружать новые текстуры огромного разрешения без измеримого эффекта.
- Для этапа 1 не требуются World Partition, сложные стриминговые системы и runtime-PCG; перейти к ним только при подтверждённой потребности.

### 15.3. Код и архитектура

- C++ — основа логики; Blueprint — настройка, контент, UI и сцепление ассетов.
- Сначала изучить реальные API модулей Toolkit. Не придумывать классы и интерфейсы за них.
- Игра зависит от уже существующих модулей; модули не зависят от `QuietRoad`.
- Не внедрять GAS, StateTree, SmartObjects, новый сетевой framework и общую инфраструктуру «на будущее».
- Не создавать монолитный Manager, ненужные абстракции и глубокие иерархии классов.
- Настраиваемые значения хранить в UPROPERTY/Data Assets там, где они нужны; избегать магических чисел и обильных констант без необходимости.
- Событийная логика вместо Tick там, где обновление каждый кадр не требуется.
- Проверять работу Blueprint/asset references после переименований, соблюдать redirectors и ссылки.

## 16. Матрица интеграции Toolkit

**Ниже — предполагаемое назначение, а не подтверждение фактических возможностей плагинов. Codex обязан сопоставить с реальными API.**

| Domain plugin | Игровой сценарий | Проверка в первой игре |
|---|---|---|
| Foundation | Инициализация и взаимодействие общих сервисов | Интеграция по реальному API |
| Interaction | Дверь, прибор, щиток, ящик, посадка | MVP, миссия 1 |
| Save | Прогресс, инвентарь, важные объекты, машина | MVP, миссия 1 |
| Items | Подобрать и применить предохранитель | MVP, миссия 1 |
| Progression | Открыть радиосканер, улучшить оборудование | MVP/миссия 1 |
| WorldMechanics | Предохранитель, рубильник, антенна | MVP, миссия 1 |
| PhysicsMechanics | Переместить препятствие и восстановить объект | Миссия 2 |
| SpawnMechanics | Управляемое появление предмета/события | Миссия 3 / тест |
| Combat | Получение урона/оружие в безопасном сценарии | Отдельный тест / опциональная зона |
| CombatMechanics | Снаряд/взрыв/эффект | Отдельный тест / опциональная зона |
| Multiplayer mechanics | Сервер + клиент, состояние и взаимодействие | Отдельная тестовая карта; не core-loop |
| Будущие plugins | Новый инструмент, задача или изолированный сценарий | Решение только после появления плагина |

**Не включать по умолчанию:** `UTExamples`, `UTShowcase`, `UTIntegrationExamples`, GAS integration, StateTree integration, SmartObjects integration. При необходимости тестов держать их отдельно от production maps.

**Наборы подключения:** базой для сюжетной игры считать `Adventure Kit` (`Foundation`, `Interaction`, `Items`, `Progression`, `Save`, `WorldMechanics`), если его реальные зависимости позволяют. `PhysicsMechanics`/`SpawnMechanics` подключать по мере возникновения соответствующей миссии; `Combat`/`CombatMechanics` — только для отдельной проверки. Не включать `Full Toolkit` ради галочки. Наличие механизмов и зависимостей сверять с репозиторием.

## 17. Этапы реализации и критерии готовности

### M0 — технический фундамент (без наполнения мира)

- Существующий Vehicle Template продолжает ездить без регрессий.
- Git/.gitignore (и, при необходимости, LFS) настроены и проверены.
- Список настоящих Toolkit plugins и их зависимостей составлен.
- Настроена простая структура проекта, входная карта и логирование.
- Имеется задокументированный способ сборки и запуска UE 5.8.

**Готово:** проект открывается, компилируется, шаблонный автомобиль едет, посторонние файлы не коммитятся.

### M1 — основной игровой прототип

- Пешеходный персонаж, переход из автомобиля и обратно, два набора управления.
- Один небольшой тестовый участок дороги и одно интерактивное устройство.
- Одна короткая завершённая задача с предметом/рубильником, где это поддерживается модулями.
- Сохранение/загрузка ключевого состояния после безопасной остановки (при наличии API Save).

**Готово:** можно доехать, выйти, выполнить задачу, вернуться, перезапустить игру и корректно восстановить прогресс.

### M2 — процедурный красивый регион

- Один компактный Landscape, дорога по spline, контролируемая PCG-растительность.
- Минимальный стилизованный художественный набор и общее освещение.
- 3–4 точки интереса без тяжёлых готовых пакетов.
- Понятные ограничения генерации: не на дороге, не на площадках и не в зоне выхода из фургона.

**Готово:** маршрут приятно выглядит, по нему возможно проехать, генерация воспроизводима, размер проекта в бюджете.

### M3 — игровые системы и мини-история

- Три миссии, простая прогрессия, журнал, инструменты и предметы.
- Физическая задача с безопасным сбросом объекта.
- Сохранение состояния разных станций, фургона и прогресса.
- Экран завершения и короткая финальная сцена.

**Готово:** игра проходится от начала до конца за один небольшой сеанс.

### M4 — необязательные интеграционные проверки

- Отдельная маленькая карта для Combat / CombatMechanics и специальных SpawnMechanics.
- По необходимости отдельная автономная тестовая карта client/server.
- Никакой обязательной кооперативной кампании.

**Готово:** результаты тестов воспроизводимы, игровой код не получил новые зависимости от тестовых сцен.

## 18. Основные риски и способы их уменьшить

| Риск | Решение |
|---|---|
| Полноценный жилой салон делает фургон слишком сложным | До позднего этапа — управляемая машина + внешние точки взаимодействия и багажник |
| Шаблонный спорткар не похож на фургон | Пока использовать как placeholder; для финала нужен отдельный корректно настроенный skeletal mesh |
| PCG блокирует дороги/двери | Exclusion volumes, проверка габаритов и clearance, фиксированные зоны миссий |
| Бесконечная генерация ломает сохранения | Конечная карта, стабильные ID, procedural — в основном декор |
| Физический предмет теряется | Кнопка/условие reset и альтернативное положение для ключевых объектов |
| Слишком много универсальной архитектуры | Реализовывать только текущий игровой срез; новые фреймворки запрещены без обоснования |
| Git разрастается | Бюджет и аудит больших файлов до каждого крупного коммита |
| Плагины имеют неожиданные зависимости | Сначала инспекция source/API и реестр интеграций, потом код |
| ИИ не может создать `.uasset` без редактора | Editor scripting / Unreal Python / MCP; честный отчёт о требуемых ручных шагах |

## 19. Что однозначно не входит в первую версию

Бесконечный мир, города, плотный трафик, полноценное дорожное ИИ, выживание с голодом/жаждой, крафт из десятков ресурсов, строительство базы, симуляция сна, свободное перемещение по движущемуся салону, online co-op campaign, процедурно сочиняемые сюжетные квесты, 20 видов оружия, продвинутые анимации, кат-сцены, фотореализм и крупные ассет-паки.

## 20. Definition of Done — игровой вертикальный срез

**Считать первый реальный результат готовым только если:**

1. Из чистой рабочей копии UE 5.8 проект открывается без отсутствующих assets/plugins.
2. Машина управляется, можно безопасно остановиться, выйти и снова сесть.
3. Работает полноценное задание с минимум одним подбором и одним применением предмета или эквивалентными существующими механизмами Toolkit.
4. Есть визуальная обратная связь и понятная цель; можно завершить миссию.
5. После сохранения и перезапуска состояние миссии/предметов не дублируется.
6. Окружение не препятствует основному маршруту; карта выглядит цельно хотя бы в одном времени суток.
7. Нет подтверждённых регрессий в стандартном управлении машиной.
8. Составлены список реально использованных модулей и список отдельно проверяемых.
9. Размер файлов и Git-истории измерен и задокументирован.
10. Код собирается; результаты запуска/тестов честно перечислены, включая ограничения среды.
